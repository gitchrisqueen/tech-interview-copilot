# Tech Interview Copilot

A real-time copilot for the interviewee in a live technical interview on **Google Meet,
Microsoft Teams, or Zoom**. It listens to the interviewers' audio (routed through BlackHole on
macOS) and your own microphone, transcribes live, detects technical questions, and instantly
drafts **verbal talking points** plus **code examples** you can walk through - with a language
switcher (Python, JavaScript, TypeScript, Java, Go, C++, SQL), documentation comments on every
example, and a select-to-explain popup for any span of code.

Answers are generated by **Ollama Cloud coding models** (through a local Ollama bridge) and
grounded with **RAG** over five public interview-prep repositories, plus your own uploaded
resume and job description so responses align with the position.

Built on [copilot-core](https://github.com/gitchrisqueen/copilot-core), a small shared package of
browser modules and Python sidecars used by this app and its sibling,
[hearing-copilot](https://github.com/gitchrisqueen/hearing-copilot). Everything here in `app/` is
this app's own domain logic (question detection, RAG, the code panel, the interview-profile
system); the transcription/speaker-ID/LLM-transport plumbing is shared.

## Intended use

This is a **demo tool for personal interview practice**, used in development by its author.
Using an assistant covertly in a real interview may violate the interviewer's policies and can
disqualify a candidacy; a permanent disclaimer stays in the app header. Practice with it, drill
with it, and treat live use as your own responsibility.

## Quickstart (macOS)

```bash
# 1) Core tools
brew install ollama blackhole-2ch

# 2) Ollama Cloud access + models
ollama signin                      # or set up your Ollama Cloud account
ollama pull nomic-embed-text       # local embedding model for the knowledge base (~274 MB)
ollama run qwen3-coder:480b-cloud "say hi"   # verify cloud model access

# 3) Secrets (optional but recommended: Together AI gives the best transcription)
cp example.env .env                # then edit .env and fill in your keys

# 4) Knowledge base (one-time, ~5-15 min; re-run any time to refresh)
cd kb
python3 -m venv venv && ./venv/bin/pip install -r requirements.txt
OLLAMA_HOST=127.0.0.1:11501 ollama serve &   # if not already running via launch.command
./venv/bin/python ingest.py

# 5) Launch (also runs `npm install` and sets up kb/venv automatically, if you skipped step 4's venv)
cd .. && ./launch.command
```

Then open the **Config** tab (bottom-right panel): pick your microphone and **BlackHole 2ch**,
watch the level meters move, and you are ready. Settings persist to `app/settings.json`
automatically.

The app ships with a **fictional demo profile** ("Acme Robotics") so it's useful out of the box.
For a real interview, see [profiles/README.md](profiles/README.md) -- your real company research
and interview strategy go in a git-ignored local folder, never in this repo.

## Routing the meeting audio (BlackHole + Multi-Output Device)

The app hears the interviewers through BlackHole, a virtual audio device. A Multi-Output Device
duplicates the meeting audio to BOTH your headphones and BlackHole, so you still hear everything.

1. `brew install blackhole-2ch`, then restart the browser.
2. Open **Audio MIDI Setup** (Applications > Utilities).
3. **+** > **Create Multi-Output Device**; check your headphones AND **BlackHole 2ch**.
   Headphones = primary device; enable Drift Correction on BlackHole.
4. In Meet / Teams / Zoom, set the **Speaker** to the Multi-Output Device (or set the whole
   system output to it).
5. In the app's Config tab, select **BlackHole 2ch** as "Interviewer audio". Play any video:
   the BlackHole meter should move.

The same steps are shown inside the app on the Config tab. **Windows** (via VB-Cable) is a
future case; this build targets macOS.

## Using it live

- **Start** (header button or Live tab) begins capture of both channels.
- **Answers tab** - every detected question becomes a card: type badge (coding / system-design /
  conceptual / behavioral / follow-up), speakable talking points, complexity, pitfalls, likely
  follow-ups, and the knowledge-base sources used.
- **Code tab** - the solution for the selected question with syntax highlighting. Language pills
  switch languages: the first switch translates the canonical solution (a few seconds), after
  that it is cached and instant. Every example carries a documentation block and inline comments.
  **Select any span of code with the mouse** and an "Explain this code" button appears; click it
  for a plain-English explanation of just that section.
- **Brief tab** - the rolling session summary plus **your own notes** (below).
- **Cheat sheets tab** - static Big-O, algorithm patterns, system design, and STAR references.
- **Prep tab** - upload your resume, the job description, and other docs (.pdf, .txt, .md).
  Resume + JD are sent with **every** answer, and each answer card carries a **"Mention from your
  documents"** block naming exactly what to say out loud from them and why it fits the question.
  Oversized "other" docs are indexed for retrieval instead. The Live tab's **Docs** chip shows
  what is actually loaded, so you can tell at a glance whether answers are being personalized.
- **Transcript** (top right) - the live transcript, with **Export** (downloads a timestamped
  .txt) and **Clear session** (wipes today's lines, answer cards, and this run's anonymous
  voices; named voices are kept). Durably logged to `logs/transcript-<date>.jsonl`.
- **Live tab** - status chips (LLM / ASR / RAG / Docs / Voices), the Voices strip, a **manual
  entry box** for typing a question the audio missed, the freshest answer's talking points, and
  an activity feed.

### The session brief (rolling summary)

A single answer is drafted from a ~25 second window, which is myopic: by minute twenty the
interview has established a stack, constraints, what you already claimed about yourself, and which
threads are still open, and none of that would reach a new answer.

Every ~25 seconds (only when the transcript actually grew) a background pass folds the new lines
into a **cumulative picture** of the session, on its own stronger, larger-context model. That
picture is then injected into every subsequent answer and code generation as binding SESSION
CONTEXT, so later answers obey constraints set earlier ("must be O(1) extra space", "we use
Postgres, not Mongo") and never contradict something you already said.

When the pass decides an existing card's answer no longer fits what the conversation has since
established, it flags it and the card is **rebuilt automatically** - the answer is redrafted and
its code regenerated against the new constraints. Rebuilt cards show an **updated vN** badge and
the reason. Each card also has a **Refresh** button to force this by hand.

**It is built not to lose context.** The pass is incremental: the model sees the summary so far
plus only the lines added since the last pass, and it answers with a *delta* (add / update /
resolve), never a rewritten summary. Anything it does not mention is kept verbatim, so a lazy or
truncated response can never silently erase what the session has learned; only an explicit
`resolve` removes an item, and topics are closed rather than deleted. If a pass fails, the
watermark does not advance, so those transcript lines are re-read on the next attempt instead of
being dropped. The raw transcript is never replaced by the summary.

The Brief tab shows all of it live: the narrative, the role context, constraints, what you have
already said, still-open threads, topics covered with status, and interviewer focus. **Summarize
now** forces a pass.

### Your notes, and keeping generated code current

The Brief tab also has a **Your notes** box. Anything you type there is **authoritative**: it is
fed into every answer and every code generation and it overrides what the app inferred from the
audio, because ASR mishears and the summarizer generalizes but a note is you stating a requirement
directly. Notes persist across reloads and are included in the transcript export. **Apply to code**
pushes them straight into the code on screen.

Generated code carries a fingerprint of the requirements it was built against - the interviewer's
constraints, the stack in play, and your notes. When those change, code that predates them is
**regenerated automatically**, even if no new question was asked ("we're a Go shop, by the way"
never used to reach the Code tab). The Code tab shows a **Requirements in effect** list, an
**Applied** line under each solution naming what that code actually honors, and if auto-update is
off (`answers.autoUpdateCode`) a **Requirements changed** banner with an Update button.

Language switching respects this too: switching languages translates the canonical solution only
when it is current. If the canonical predates a requirement, the target language is generated
fresh rather than translating a stale solution forward.

### Multiple interviewers (voice profiles)

Each interviewer utterance is fingerprinted by the voice sidecar, so a panel of interviewers is
split into separate voices (V1, V2, ...) instead of one anonymous "Interviewer". On the Live tab,
the **Voices heard** strip shows one pill per voice: click one to **name it** ("Sarah (hiring
manager)"), and every line of that voice - past and future - is relabeled in the transcript and
in exports. If a line is attributed to the wrong person, the dropdown at the end of the transcript
row reassigns it, and that correction also teaches the voice profile.

Named voices persist under `voice-profiles/<session>/` keyed by `speakerId.scopeId` in the
Config, so the same interviewer is recognized in a later round. These are biometric-adjacent voice
fingerprints of real people: they stay local and are git-ignored. Without the sidecar running the
app behaves exactly as before, with every remote line labeled "Interviewer".

### Typing a question the app missed

Audio drops, someone talks over the question, or it arrives in the meeting chat. The **manual
entry box** on the Live tab takes any typed question and runs it through the identical pipeline
(detection, retrieval, answer, code). It lands in the transcript labeled "Typed", so the export
still reflects the whole interview.

Everything degrades gracefully: no summarizer -> answers still work from the per-question window;
no LLM -> an offline heuristic detector still spawns cards with
matched topics and raw study material (retrieval is local); no Together key -> local whisper.cpp;
no whisper -> the browser's Web Speech engine; no RAG server -> answers without references.

## The knowledge base

`kb/ingest.py` shallow-clones and indexes these repositories at runtime, on your own machine
(manifest: `kb/repos.json`). None of their content is redistributed in this repo -- see the
license note below.

1. [FAANG-Coding-Interview-Questions](https://github.com/ombharatiya/FAANG-Coding-Interview-Questions)
2. [tech-interview-handbook](https://github.com/yangshun/tech-interview-handbook)
3. [ai-engineering-field-guide](https://github.com/alexeygrigorev/ai-engineering-field-guide)
4. [ai-interview-codex](https://github.com/girijesh-ai/ai-interview-codex)
5. [LeetCode-Solutions](https://github.com/kamyu104/LeetCode-Solutions) (Python solutions + the
   README complexity tables; capped - the full repo is ~3.5k problems in several languages)

Chunks are embedded with `nomic-embed-text` on the **local** Ollama server (no cloud dependency
for retrieval) into `kb/index/kb.sqlite` (~25-35k chunks, ~100-250 MB). `app/rag-server.py`
serves it with brute-force cosine search over an in-memory numpy matrix - at this scale a
vector database would add dependencies for no perceptible gain.

The clones and the built index are **git-ignored by design**: they are rebuildable in minutes
with one command, they would bloat the repo by hundreds of MB, and **each source repo carries its
own license** -- this project clones them locally for retrieval only and never redistributes
their content; check each repo's own license before relying on its content beyond personal study.
Re-run `./venv/bin/python ingest.py` any time; it is incremental by content hash.

**Why RAG and not fine-tuning:** fine-tuning a 480B cloud model is not possible, and fine-tuning
a small local model would cost days of data-prep and GPU time to bake in static knowledge that
goes stale the moment the source repos update - and it would still reason worse than
qwen3-coder-480B. RAG gives the strong cloud model the same material at answer time, rebuilds in
minutes, and shows its sources.

## Configuration

- **Config tab (persisted to `app/settings.json`)** - audio devices, answer/detection models,
  timeouts, default code language, verbosity, RAG on/off + top-k, transcription engine.
- **`.env` (git-ignored, template `example.env`)** - `TOGETHER_API_KEY` (hosted transcription),
  `OPENAI_API_KEY` / `GROQ_API_KEY` (LLM fallbacks). Injected into `config.js` at serve time by
  `web-server.py`; keys never enter the repo or the settings file.
- **`app/config.js`** - committed defaults for everything above, plus `window.CopilotCore` (the
  namespace and hooks copilot-core's shared modules read -- see that project's README).
- **`kb/repos.json`** - the ingestion manifest (repos, include globs, chunking, embedding model).

## Architecture and ports

```
mic + BlackHole -> asr.js (VAD chunking, WAV) -> Together /asr proxy | whisper.cpp | webspeech
     -> transcript (TLOG + log-server) -> qa.js rolling window
     -> llm.js detectQuestion -> rag-server /query + /docs/context
     -> llm.js composeAnswer -> Answer card -> generateCode/translateCode -> Code panel
                                                        -> explainCode (select-to-explain)
     (each interviewer chunk is also fingerprinted by speaker-server -> named voices in the
      transcript; typed manual entries join the pipeline at the qa.js step)
```

| Service | Port | Required | Source |
|---|---|---|---|
| `app/web-server.py` - static app + .env injection | 8877 | yes | thin wrapper over `copilot_core.webserver` |
| `app/log-server.py` - transcript log, /settings, /asr proxy | 8890 | yes | thin wrapper over `copilot_core.logserver` |
| `app/speaker-server.py` - voice profiles (multiple interviewers) | 8891 | optional | app-local, uses `copilot_core.speaker.engine` |
| `app/rag-server.py` - retrieval + candidate docs | 8892 | optional | app-local |
| `ollama serve` - bridge to Ollama Cloud + embeddings | 11501 | for LLM/RAG | external |
| whisper.cpp server - local ASR fallback | 8189 | optional | external |

All ports are distinct from the sibling hearing-copilot project, so both can run at once.
Frontend: vanilla JS, no bundler, no build step, no CDN -- `js/*.js` from `@gitchrisqueen/copilot-core`
plus this app's own `app/*.js`, loaded via plain `<script>` tags (see `index.html` for the required
order). Backend: Python 3 stdlib sidecars (the only pip deps are `numpy`, `pypdf`, `sherpa-onnx`,
and `copilot-core` itself, all in the `kb/venv` that `launch.command` sets up automatically).

## Troubleshooting

- **No BlackHole in the device list** - install it, then fully restart the browser; re-check
  with Refresh devices on the Config tab.
- **Interviewer meter silent** - the meeting's Speaker (or system output) is not set to the
  Multi-Output Device, or the Multi-Output Device is missing BlackHole 2ch.
- **LLM chip red** - is `ollama serve` running on 11501? Does `ollama run qwen3-coder:480b-cloud
  "hi"` work (cloud sign-in)? Fallback keys in `.env`?
- **Transcription poor or missing** - without a Together key it uses local whisper.cpp (start it
  via launch.command with a model) or Web Speech. Add `TOGETHER_API_KEY` for the best quality.
- **`ingest.py` fails with HTTP 404 from Ollama** - the server on 11501 either does not have
  `nomic-embed-text` (the script now checks at startup and auto-pulls it; manual fix:
  `OLLAMA_HOST=127.0.0.1:11501 ollama pull nomic-embed-text`) or is an old Ollama build without
  the `/api/embed` endpoint (pre-v0.3.0; the script falls back to the legacy endpoint
  automatically, but upgrading is recommended: `brew upgrade ollama`). If 11501 is down
  entirely, the script now tries the default Ollama instance on 11434 before giving up.
- **RAG chip red / no sources on cards** - build the index (`kb/ingest.py`) and ensure the kb
  venv exists so `rag-server.py` has numpy.
- **Docs chip says "none" after uploading** - the rag-server must be running (it holds the
  uploads). The app re-checks every 30 s, so starting it later is fine, no reload needed.
- **Voices chip off / everyone is "Interviewer"** - the voice sidecar needs `sherpa-onnx` in the
  kb venv (`cd kb && ./venv/bin/pip install -r requirements.txt`) and the ~28 MB CAM++ model that
  launch.command downloads on first run. Optional feature; nothing else breaks without it.
- **Two voices for the same person** - happens when someone's audio changes noticeably mid-call.
  Name both the same thing, or reassign a line with the transcript dropdown to teach the profile.
- **Together 503s** - their serverless tier throttles bursts; the app serializes calls, retries,
  and falls back to local whisper automatically.
- **`node_modules/@gitchrisqueen/copilot-core` missing / core scripts 404** - run `npm install`
  from the repo root (launch.command does this automatically on first run).

## Limitations and future work

- Windows audio routing (VB-Cable) - future case; macOS only today.
- Voice profiles identify WHO is speaking, they do not split one audio chunk containing two
  overlapping speakers.
- `.docx` uploads - export to PDF or text for now.
- ScriptProcessorNode is deprecated (still works everywhere); an AudioWorklet port is a
  contained future task inside copilot-core's `asr.js`.
- Code generation on the 480B cloud model runs ~5-15 s; talking points always render first.

## Development, testing, and contributing

```bash
npm install && npm test          # node:test, against app/profile.js and app/rag.js
```

Test coverage is intentionally honest, not padded: `profile.js`/`rag.js` are well covered;
`app.js`/`qa.js`/`summary.js`/`codepanel.js`/`hl.js`/`llm.js` are large DOM-driven or prompt-heavy
modules with little coverage yet. `codecov.yml`'s project target tracks the real measured baseline
and only ratchets up as tests are added -- see [CONTRIBUTING.md](CONTRIBUTING.md) for the branch
protection and CI setup, including how a solo maintainer satisfies a required-review gate.
